# korvid v0.7.0

## Why upgrade

- **`:blocked` explains why a workload has no Pods.** For a Deployment,
  ReplicaSet, StatefulSet, DaemonSet, Job or CronJob, it shows the creation
  failures the controller recorded, next to the namespace's ResourceQuotas and
  LimitRanges, with quantities compared exactly. A Possible constraints
  section checks what the next Pod, and a StatefulSet's new claims, ask for
  against those policies as now observed. Each row is a possibility, never a
  cause. See
  [workload creation failures](https://hellices.github.io/korvid/tui/#workload-creation-failures).
- **`:consumers` shows who uses a ConfigMap or Secret** and what a change means
  for each: environment variables, mounted volumes, `subPath` mounts and image
  pull secrets. Reopened after the object changed, it says whether the change
  followed each consumer's start. See
  [configuration propagation](https://hellices.github.io/korvid/tui/#configuration-propagation).
- **A CRD installed during a session opens without a restart.** An unknown `:`
  command reads the cluster's API resources again before it is reported, and
  `:rediscover` reads them now. See
  [reading the cockpit](https://hellices.github.io/korvid/tui/#read-the-cockpit).
- **`y` copies to the clipboard**: the open describe view, or the selected
  resource's name. See
  [keybindings](https://hellices.github.io/korvid/keybindings/#move-and-inspect).
- **MCP hosts get tool hints.** Every tool in `tools/list` has a title and
  read-only, destructive, idempotent and open-world hints, so a host can allow
  read-only tools without asking. See
  [tool hints](https://hellices.github.io/korvid/mcp/#tool-hints).

Every new view says what its evidence does not establish: a source the
cluster refused, a list cut short or one gone stale is named, never read as
absence. These features complete the v0.7.0 work tracked by
[milestone 9](https://github.com/hellices/korvid/milestone/9).

## Breaking changes and migration

The configuration format is unchanged from v0.6.0. Two new defaults can affect
an existing configuration:

- **`y` is now the default key of Copy.** A `keybindings:` override that maps
  another action to `y` is skipped at startup with a warning, and that action
  keeps its default key. To keep `y` for it, move Copy first, for example with
  `copy: f9`. See the
  [keybinding guide](https://hellices.github.io/korvid/keybindings/#remap-an-app-action).
- **`:blocked`, `:consumers`, `:config-consumers` and `:rediscover` are
  built-in commands,** and a built-in command wins over a resource name. Open a
  custom resource whose plural or short name is one of these by its qualified
  name, for example `:blocked.example.com`.

## Reliability and safety

- v0.7.0 ships the dependency updates of
  [v0.6.1](https://hellices.github.io/korvid/release-notes/v0.6.1/):
  `certifi` 2026.10.19 (critical), `aiohttp` 3.14.4, `filelock` 4.2.4 and
  `litellm` 1.100.4 (high), and `opentelemetry-api` 1.45.1 (moderate), with
  its shutdown and Intel Homebrew fixes. Upgrading from v0.6.0 brings them even
  where v0.6.1 was never installed.
- The new views read only what they show: `:blocked` reads the workload, its
  ReplicaSets or Jobs, the namespace's Events, quotas and LimitRanges, and
  keeps only the template's requests, limits and scheduling fields, never an
  environment value, command or image. Their reads are bounded and dropped on
  a context switch.
- Reading the API resources again is rate-limited for unknown commands, never
  runs during a context switch, and never moves a name an open view uses to
  another API group.

The safety perimeter is unchanged. Agent investigation remains read-only.
Agent writes remain structured tools with no shell. The resolved policy arms
only exact registry tool names, import-time metadata validates dispatch, and
`ToolExecutor` rejects an unknown tool. It performs typed argument validation
before every dispatch. Every write opens an approval dialog, requires a fresh
approval keystroke, and revalidates the exact target UID. MCP tool hints do
not change any of this. Results still pass through masking, `y` copies only
the masked text a view shows, and audit logging remains fail-closed.

## Kubernetes versions verified

Kubernetes 1.33, 1.34, 1.35 and 1.36, by the Kubernetes version matrix on
throwaway kind clusters, which now also covers the creation-failure and
configuration-propagation reads.

## Install or upgrade

Install with `uv`:

```bash
uv tool install 'korvid[all]==0.7.0'
```

Reinstall the exact version with `uv` or `pipx` when upgrading:

```bash
uv tool install --force 'korvid[all]==0.7.0'
pipx install --force 'korvid[all]==0.7.0'
```

Homebrew users get v0.7.0 from `brew upgrade korvid` once the tap is updated.

## Verify

After the maintainer publishes the
[GitHub release](https://github.com/hellices/korvid/releases/tag/v0.7.0),
download its artifacts, verify both attestations, and check the wheel against
the checksum manifest:

```sh
set -eu
gh release download v0.7.0 --dir dist/v0.7.0 --repo hellices/korvid
gh attestation verify dist/v0.7.0/korvid-0.7.0-py3-none-any.whl --repo hellices/korvid
gh attestation verify dist/v0.7.0/SHA256SUMS --repo hellices/korvid
(cd dist/v0.7.0 && shasum --algorithm 256 --check SHA256SUMS)
uvx --from 'korvid[all]==0.7.0' korvid --version
```

The final command must report `korvid 0.7.0`.

## Known limits

- `:blocked` never forecasts the next create: quota status is not a
  reservation, admission webhooks are not observed, and a rolling update's
  surge Pods are not computed. Node capacity and scheduling are out of scope.
- `:consumers` judges whether a change followed a consumer only between two
  openings in the same session; korvid keeps no history across restarts.
- `y` relies on the terminal accepting OSC 52 clipboard writes, which some
  terminals and multiplexers disable or do not support.
- MCP tool hints are advice for the host's prompting only.
- This source candidate does not itself publish PyPI, GitHub, or Homebrew
  artifacts. Use the verification steps after the maintainer publishes the
  release.
