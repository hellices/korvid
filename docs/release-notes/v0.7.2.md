# korvid v0.7.2

v0.7.2 is a dependency update to v0.7.1. It changes no feature: everything
in the
[v0.7.0 release notes](https://hellices.github.io/korvid/release-notes/v0.7.0/)
and the
[v0.7.1 release notes](https://hellices.github.io/korvid/release-notes/v0.7.1/)
still applies.

## Why upgrade

The `[agent]` extra pins LiteLLM exactly, and the Homebrew formula installs
exactly the versions a release was tested with, so neither moves until korvid
is released again. v0.7.1 ships LiteLLM 1.100.4, which dependency scanners
flag. Its agent also fails to start when a newer LiteLLM is installed into the
same environment, because LiteLLM 1.104.0 removed a setting korvid checks for
when it loads LiteLLM. v0.7.2 ships a current LiteLLM and a fixed
`opentelemetry-api`.

## Dependency updates

| Package | v0.7.1 ships | v0.7.2 ships | Why |
| --- | --- | --- | --- |
| `litellm` | 1.100.4 | 1.109.1 | scanners flag 1.100.4; newer releases broke the agent's startup check |
| `opentelemetry-api` | 1.45.1 | 1.45.2 | moderate: CVE-2026-126360, slow `traceparent` parsing that can deny service |
| `pydantic` | 2.13.4 | 2.14.4 | LiteLLM 1.109.1 needs 2.14 on newer Pythons; korvid ships one release everywhere |

- **LiteLLM.** The removed setting, `litellm.telemetry`, was not read anywhere
  in LiteLLM, so it never switched anything off. korvid still sets the other
  seven settings that keep prompts, tool arguments and debug output on your
  machine, and still refuses to start the agent if one of them disappears.
  The [threat model](https://hellices.github.io/korvid/threat-model/) lists
  them.
- **Truncated answers.** LiteLLM now rejects a provider stream that stops
  before the answer finishes. korvid still reports that as a truncated answer,
  not as an unavailable provider.
- **`opentelemetry-api`** comes in through the MCP SDK in the `[mcp]` extra.
- The MCP SDK, Starlette, `httpx2`, `azure-identity` and the AWS SDK move to
  their current patch or minor releases with the rest of the runtime set.

The safety perimeter is unchanged. Agent investigation remains read-only.
Agent writes remain structured tools with no shell. The resolved policy arms
only exact registry tool names, import-time metadata validates dispatch, and
`ToolExecutor` rejects an unknown tool. It performs typed argument validation
before every dispatch. Every write opens an approval dialog, requires a fresh
approval keystroke, and revalidates the exact target UID. Results still pass
through masking, and audit logging remains fail-closed.

## Kubernetes versions verified

Kubernetes 1.33, 1.34, 1.35 and 1.36, by the Kubernetes version matrix on
throwaway kind clusters.

## Install or upgrade

Install with `uv`:

```bash
uv tool install 'korvid[all]==0.7.2'
```

Reinstall the exact version with `uv` or `pipx` when upgrading:

```bash
uv tool install --force 'korvid[all]==0.7.2'
pipx install --force 'korvid[all]==0.7.2'
```

Homebrew users get v0.7.2 from `brew upgrade korvid` once the tap is updated.

## Verify

After the maintainer publishes the
[GitHub release](https://github.com/hellices/korvid/releases/tag/v0.7.2),
download its artifacts, verify both attestations, and check the wheel against
the checksum manifest:

```sh
set -eu
gh release download v0.7.2 --dir dist/v0.7.2 --repo hellices/korvid
gh attestation verify dist/v0.7.2/korvid-0.7.2-py3-none-any.whl --repo hellices/korvid
gh attestation verify dist/v0.7.2/SHA256SUMS --repo hellices/korvid
(cd dist/v0.7.2 && shasum --algorithm 256 --check SHA256SUMS)
uvx --from 'korvid[all]==0.7.2' korvid --version
```

The final command must report `korvid 0.7.2`.

## Known limits

- v0.7.2 changes no behaviour, so the known limits in the
  [v0.7.0 release notes](https://hellices.github.io/korvid/release-notes/v0.7.0/)
  still apply.
- This source candidate does not itself publish PyPI, GitHub, or Homebrew
  artifacts. Use the verification steps after the maintainer publishes the
  release.
