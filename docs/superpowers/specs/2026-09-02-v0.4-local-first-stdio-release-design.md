# v0.4.0 Local-First Stdio Release Design

- Date: 2026-09-02
- Target: `v0.4.0`
- Status: Approved for execution

## Release theme

`v0.4.0` is the local-first MCP release. It replaces direct loopback HTTP as
the normal local client setup with a stdio adapter that reuses the running TUI,
while completing the local write-safety, provider-stream, Kubernetes error, and
loopback-authentication prerequisites needed to ship that transport safely.

The release is defined by a coherent user-visible capability, not by elapsed
time or an arbitrary number of merged issues.

## Included work

Issues #331 and #330 are already complete and form the outbound-data redaction
foundation.

The remaining release blockers are implemented and merged in this order:

1. #332 — reset namespace when changing to a context without one
2. #333 — do not surface write approval while an inline editor owns input
3. #334 — fail closed when Pod identity cannot be revalidated before transfer
4. #335 — revalidate Helm release incarnation before mutation
5. #336 — reject truncated provider streams and bound hidden buffers
6. #344 — normalize Kubernetes transport and malformed-response failures
7. #329 and #346 — ship the internal loopback capability and stdio-default
   adapter together

Issue #335 is a blocker rather than conditional work because Helm upgrade,
rollback, and uninstall are currently documented and exposed product
capabilities.

## GitHub milestone

Track the scope in an open GitHub milestone named `v0.4.0`, without an
arbitrary calendar due date. The milestone contains:

- completed foundation: #330 and #331;
- remaining blockers: #329, #332, #333, #334, #335, #336, #344, and #346;
- parent completion issue: #348.

The milestone is the source of truth for release progress. Do not add #342,
#307, #347, or any `status: backlog` issue. Adding or removing a milestone
issue requires the same explicit scope review as changing this design.

After each PR merge, verify the issue closed and the milestone counts changed.
Close the milestone only after #348 is closed and the release preparation PR
has established the exact `v0.4.0` release commit.

## Excluded work

- #342 is an optional small custom-column crash fix and does not block the
  release.
- #307 is a separate agent/evaluation architecture initiative and does not
  block the local-first MCP capability.
- Issues labeled `status: backlog` do not enter this release.
- OAuth, remote public HTTP, and headless MCP remain deferred under #347.

If an excluded issue becomes a direct blocker for an included issue or a
required release check, it may be promoted only with explicit scope review.

## Development workflow

Each issue uses its own branch and project-local worktree based on the latest
`origin/main`.

For every issue:

1. verify that it is not labeled `status: backlog`;
2. inspect the current implementation and all affected security boundaries;
3. write and approve a focused design and implementation plan;
4. implement with TDD;
5. run targeted checks while iterating and the repository gate before
   publication;
6. create a PR automatically after implementation;
7. run the `AGENTS.md` review loop, including suppressed findings;
8. fix credible findings, reply to each thread, and resolve it;
9. stop speculative Copilot review after two consecutive low-confidence-only
   rounds with no blocking findings;
10. report the result in the conversation rather than creating a separate
    development-report file;
11. wait for the maintainer to merge.

The next issue starts only after the preceding PR is merged, so every worktree
is based on the actual release line rather than a stack of unmerged branches.

## Coupled delivery of #329 and #346

#329 must not ship alone. Protecting the loopback endpoint without the stdio
adapter would force existing direct HTTP users to manage an internal
capability token.

#329 and #346 therefore share one delivery milestone:

- they may use separate implementation commits or reviewable sub-branches;
- the public merge sequence must not leave `main` documenting or requiring
  manual management of the internal capability;
- client-facing examples switch directly to `korvid mcp stdio`;
- the capability remains owner-only internal plumbing and is never printed,
  logged, audited, or returned.

## Release readiness point and notification

The release candidate becomes ready immediately after the reviewed #329+#346
delivery is merged and issue #348's completion criteria are satisfied.

At that point, stop feature development and notify the maintainer:

> `v0.4.0` feature scope is complete. The local-first stdio milestone is ready
> for release preparation.

Do not create a release tag at that notification point.

## Release preparation

After the readiness notification, create a release-only branch and PR that:

1. updates the package version from `0.3.0` to `0.4.0`;
2. updates the release runbook and release scripts from `v0.3.0` to `v0.4.0`;
3. adds release notes summarizing the local-first stdio capability and safety
   fixes;
4. validates the supported upgrade source from `0.3.0`;
5. runs the full repository and release-script gates;
6. runs the non-publishing `Release` workflow dry run on the reviewed `main`
   commit after the release PR is merged;
7. records the exact release commit and confirms all required checks are green.

The maintainer receives a second notification when these reversible checks
pass:

> `v0.4.0` release preparation and dry run are green. The reviewed commit is
> ready for the protected tag and release-environment approval.

Creating and pushing `v0.4.0` is irreversible release work and requires the
maintainer's explicit instruction at that time.

## Go/no-go gate

Release preparation is **go** only when:

- every included issue is closed by a merged PR;
- #329 and #346 are both present on `main`;
- #348 is complete;
- all required CI checks on the release PR are successful;
- no unresolved review thread remains;
- the branch and `uv.lock` are clean;
- package version, runbook, scripts, release notes, and upgrade source all say
  `0.4.0` consistently;
- the non-publishing release dry run succeeds from the exact reviewed `main`
  commit.

Any failed gate is a **no-go**. Do not weaken checks, move tags, reuse a
published version, or bypass protected-environment approval.

## Success criteria

Users can configure a local MCP client with `korvid mcp stdio`, reach exactly
one selected running TUI, and use the existing read, UI, follow,
observability, proposal, approval, context/identity, and audit behavior
without seeing or managing the internal loopback capability.

The minor release is complete only after the protected release workflow
publishes `v0.4.0` successfully and the published artifacts, attestations,
checksums, PyPI installation, upgrade from `0.3.0`, and GitHub Release are
verified.
