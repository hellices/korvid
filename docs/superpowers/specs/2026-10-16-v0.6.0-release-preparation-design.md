# v0.6.0 Release Preparation Design

**Issue:** [#421](https://github.com/hellices/korvid/issues/421)
**Release:** v0.6.0
**Status:** Approved for implementation

## Purpose

Prepare the reviewed source changes for a v0.6.0 release without crossing any
irreversible publication boundary. The preparation must turn the current
unreleased feature documentation into exact release metadata, qualify the
integrated #404, #405, and #406 behavior, and leave a source branch ready for
maintainer review.

This phase does not dispatch the exact-main release dry run, create or push a
tag, publish to PyPI, create or finalize a GitHub Release, or initiate the
Homebrew handoff. Those steps require the preparation pull request to be merged
and separately authorized by the maintainer.

## Considered Approaches

### Source-only preparation pull request

Update release metadata, documentation, and qualification coverage on a branch
from current `origin/main`; run the repository quality gate; then hand off the
source branch. A pull request is opened only after an explicit maintainer
request. This is the selected approach because the maintained release workflow
only supports a meaningful dry run from the exact reviewed `main` revision.

### Preparation plus dry run

Prepare the source and immediately dispatch the release workflow. This is
rejected for this phase because a branch dry run would not prove the exact
merged source, while the supported workflow intentionally validates live
`origin/main`.

### Full pre-publication execution

Prepare source, create the release tag, and proceed to protected publication
jobs. This is rejected because tags, attestations, and PyPI publication are
irreversible or externally protected actions and the current request is release
preparation, not publication authorization.

## Source Changes

### Release metadata

Update `[project].version` in `pyproject.toml` from `0.5.0` to `0.6.0`.
Update `[tool.korvid.release].upgrade-from` from `0.4.1` to `0.5.0`.

Any generated or checked release metadata must continue to derive from
`pyproject.toml`; do not add a second version source. The lockfile changes only
if the repository's release procedure requires an intentional, index-neutral
lock update. A developer's corporate-mirror rewrite must never be staged.

### Release notes and documentation

Promote the current unreleased v0.6.0 content into
`docs/release-notes/v0.6.0.md`. The notes describe only implemented behavior:

- staged keybinding editing with guided conflict resolution and independent
  reset;
- stable per-cluster namespace shortcuts and explicit repack;
- bounded Deployment scale/restart outcome observation;
- retained security, approval, audit, identity, and optional-extra boundaries.

Replace `docs/release-notes/unreleased.md` with a short next-development page
that identifies v0.6.0 as the latest prepared release without claiming it is
published before publication occurs. Update the documentation navigation to
include v0.6.0 and keep the capability ledger consistent with the implemented
surfaces.

Documentation must distinguish source preparation from publication. Before the
tagged release is verified, wording may call v0.6.0 the prepared or candidate
release, but not the latest published release.

### Integrated release contracts

Add or update focused tests only where current coverage does not already pin the
release integration contract:

- version and supported upgrade source are `0.6.0` and `0.5.0`;
- v0.6.0 notes are included in the public documentation site;
- unreleased notes no longer describe v0.5.0 as the next candidate;
- #404 and #406 retain independent reset/reallocation state;
- #405 remains bounded, context-safe, UID-safe, and downstream of durable
  mutation success audit.

Do not duplicate feature suites that already prove these behaviors. Reuse
existing release-policy, documentation, keybinding, namespace-slot, and
Deployment-outcome tests.

## Qualification Flow

1. Make changes on `agents/release-v0.6.0`, based on current `origin/main`.
2. Run targeted release metadata and documentation tests while iterating.
3. Run the full repository quality gate before committing the final source.
4. Verify the diff contains no corporate-mirror lockfile URLs, generated
   artifacts, credentials, tags, workflow dispatches, or publication changes.
5. Commit the source preparation and report the exact head revision.
6. Push or open a normal pull request only after explicit maintainer
   instruction. A later pull request references #421 but does not close it.

Issue #421 remains open after the preparation pull request. Its later exit
criteria include exact-main dry-run qualification and verified PyPI, GitHub
Release, and Homebrew publication.

## Error Handling

- A release metadata or documentation contract failure blocks the preparation
  pull request.
- A local full-gate failure caused solely by an intentionally preserved,
  unstaged corporate-mirror `uv.lock` rewrite must be reported explicitly and
  verified on the clean committed revision in CI; it must not be hidden,
  staged, reset, or used to weaken a gate.
- Any unexpected source, lockfile, artifact, or generated-file change stops
  preparation until its provenance is understood.
- No failed preparation step is recovered by tagging, publishing, bypassing
  hooks, or weakening tests.

## Verification

Targeted verification covers release config, release scripts, documentation
site contracts, navigation, readability, and any integration tests changed in
this work. Final verification uses `make check`, source-size and architecture
checks included by repository policy, plus `git diff --check`.

After the preparation pull request is merged, a separate maintainer-approved
phase checks out the exact `origin/main` revision and follows `docs/release.md`
for the non-publishing dry run and cross-version upgrade gate. Publication
requires another deliberate authorization.

## Acceptance Criteria

- Release metadata reports version `0.6.0` and upgrade source `0.5.0`.
- v0.6.0 notes accurately summarize #404, #405, and #406 without including
  deferred #408 or v0.7.0 scope.
- Documentation navigation and the capability ledger match the prepared source.
- Targeted and full quality gates pass on the exact committed source, with any
  local-only lockfile constraint disclosed.
- The prepared branch contains no tag, workflow dispatch, attestation,
  publication, or Homebrew merge action.
- No push or pull request occurs without explicit maintainer instruction.
- #421 remains open for exact-main dry run and publication verification.
