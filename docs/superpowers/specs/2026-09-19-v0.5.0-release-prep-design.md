# v0.5.0 Release Preparation Design

## Status

Approved by the `v0.5.0` milestone, release tracker #387, and the maintainer's
instruction to continue after #403 merged.

## Goal

Prepare one reviewable, reversible source change for korvid `v0.5.0`. The
change makes the repository describe exactly what will be published, but it
does not create a tag, publish an artifact, or trigger any irreversible release
boundary.

## Scope

The preparation branch contains four kinds of change:

1. Release metadata moves from `0.4.1` to `0.5.0`, with `0.4.1` as the
   supported cross-version upgrade source.
2. The accumulated Unreleased material becomes a concise, user-facing
   `v0.5.0` release note. The Unreleased page returns to a short empty-state
   page for work after the release candidate.
3. A compact internal capability ledger records current product decisions with
   the vocabulary `implemented`, `partial`, `validated`, `deferred`, and
   `rejected`. The original 2026-07 design is marked historical where current
   architecture and the ledger supersede it.
4. Repository contracts, generated lock metadata, documentation navigation,
   and release artifacts are validated from the prepared source.

Publication is explicitly outside this branch. The Release workflow dry run,
annotated tag, PyPI publication, GitHub Release finalization, and Homebrew
handoff happen only after this preparation change is reviewed and merged to
`main`.

## Release metadata

`pyproject.toml` is the canonical release configuration:

- `project.version = "0.5.0"`
- `tool.korvid.release.upgrade-from = "0.4.1"`

`src/korvid/__init__.py` must expose the same version. `uv.lock` is regenerated
only with all user and environment index overrides disabled, so its package
record changes without rewriting public artifact URLs to a corporate mirror.

A release-specific contract test pins the version, upgrade source, and runtime
version together. Existing release policy tests continue to prove that the
upgrade source is the previous minor line and has published release notes.

## Release notes

`docs/release-notes/v0.5.0.md` is intentionally shorter than the accumulated
Unreleased page. It contains:

1. **Why upgrade**: Pulse / Problems and the searchable Action Palette.
2. **Breaking changes and migration**: only required operator action, with at
   most one compact configuration example and links to maintained guides.
3. **Reliability and safety**: grouped outcomes for Windows input readiness,
   bounded Kubernetes/transport cleanup, provider diagnostics, and unchanged
   approval/audit guarantees.
4. **Install or upgrade**: pinned `uv tool` and `pipx` commands required by the
   release contract.
5. **Verify**: GitHub artifact, attestation, and checksum commands required by
   the release contract.
6. **Known limits**: bounded Pulse evidence, no fleet/multi-cluster view, no
   arbitrary Action Palette commands, and no autonomous write approval.

The note links the `v0.5.0` milestone for exhaustive issue history rather than
listing issue numbers. It retains the self-hosted streaming recovery required
by the current documentation contract: a connection-test response over 4,096
characters is refused, and incomplete stream signals link to the maintained
agent troubleshooting section.

`docs/release-notes/unreleased.md` becomes a small page stating that no changes
have been recorded after the `v0.5.0` release candidate. The release navigation
keeps Unreleased first, then `v0.5.0`, then earlier history.

## Capability ledger

`docs/dev/capabilities.md` is an internal living table, not a public roadmap.
Each row has one of five states:

- `implemented`: shipped behavior with maintained user documentation;
- `validated`: implemented and qualified by explicit cross-platform,
  integration, or evaluation evidence;
- `partial`: shipped with a deliberately bounded surface;
- `deferred`: plausible future work that is not committed to a release;
- `rejected`: a direction intentionally excluded from korvid's product model.

The ledger covers the major TUI, safety, Agent/MCP, observability, evaluation,
and extension surfaces. It states that the public plugin contracts are
`korvid.provider` and `korvid.credential`; arbitrary panel/tool plugins are not
public contracts. It also records that autonomous writes and approval bypass
are rejected.

`docs/dev/README.md` links the ledger. The original
`docs/dev/specs/2026-07-23-korvid-tui-design.md` is marked as a historical
baseline and points readers to the current architecture and capability ledger.

## Validation and handoff

The preparation branch must pass:

- targeted release metadata, release policy, lockfile, capability-ledger, and
  documentation tests;
- strict MkDocs build and `scripts/check_docs_site.py`;
- wheel and sdist build plus `scripts/release/check_artifacts.py`;
- the complete repository gate, formatting, deptry, and pre-commit.

After review and merge, the maintainer runs the non-publishing Release workflow
dry run from the exact `main` revision, performs the required cross-version
upgrade qualification from `0.4.1`, and only then creates the annotated
`v0.5.0` tag. The agent does not merge the preparation PR, create the tag, or
publish.
