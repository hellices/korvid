# v0.4.0 Local-First Stdio Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver and publish `v0.4.0` as the complete local-first stdio MCP milestone.

**Architecture:** GitHub milestone `v0.4.0` is the release source of truth. Every blocker uses an independent latest-main worktree, focused design and implementation plan, TDD, PR, review loop, and maintainer merge; #329 and #346 form one coupled delivery boundary. Release preparation begins only after the milestone feature scope is complete.

**Tech Stack:** Python 3.11–3.13, Textual, Kubernetes asyncio client, MCP SDK, uv, pytest, Ruff, mypy, Tach, GitHub Actions, PyPI Trusted Publishing

## Global Constraints

- Milestone issue set is exactly #329, #330, #331, #332, #333, #334, #335, #336, #344, #346, and #348.
- Completed foundation is #330 and #331.
- Remaining order is #332, #333, #334, #335, #336, #344, then #329 and #346 together.
- #342, #307, #347, and every `status: backlog` issue are excluded.
- Each issue starts from the latest merged `origin/main`; do not stack unmerged feature branches.
- Each implementation ends with automatic PR creation, AGENTS.md review rounds, CI verification, and an in-chat report.
- Never merge automatically; the maintainer merges reviewed PRs.
- Never re-lock through the corporate mirror or commit a proxy-specific `uv.lock`.
- Notify the maintainer when feature scope is complete, then again when release preparation and dry run are green.
- Do not create or push the protected `v0.4.0` tag without explicit maintainer instruction.

### Task 4: Deliver authenticated stdio as one milestone

**Files:**
- No shared implementation file. The coupled delivery design must declare
  exact MCP server, CLI, endpoint-registry, and test paths before code changes.

**Interfaces:**
- Consumes: complete local safety and reliability baseline
- Produces: authenticated internal loopback bridge plus `korvid mcp stdio`

- [ ] **Step 1: Design #329 and #346 together**

Write separate reviewable implementation tasks but one shared delivery design
that guarantees:

```text
MCP host -> stdio -> korvid mcp stdio
         -> owner-only endpoint registry + per-run capability
         -> running Korvid TUI
```

The design must prohibit user-managed capability tokens, a second KubeClient,
a daemon, a new IPC protocol, and a headless write path.

- [ ] **Step 2: Implement the internal capability**

Implement #329 with TDD, including authentication-before-parsing,
constant-time comparison, owner-only registry publication, rotation,
non-oracle rejection, publication failure, and no-log/no-audit guarantees.

Do not merge a state that requires users to configure the capability manually.
If separate PRs are used, keep the capability PR blocked until the stdio PR is
ready for the same coordinated merge window.

- [ ] **Step 3: Implement the stdio adapter**

Implement #346 with TDD, including no/stale/multiple-instance selection,
`--instance <pid>`, list/call forwarding, cancellation, token rotation, and
end-to-end stdio tests.

- [ ] **Step 4: Review and merge the coupled delivery**

Run full review rounds on both changes. Before maintainer handoff, verify the
combined result rather than either branch alone:

```bash
UV_FROZEN=1 make check
PR_329=$(gh pr list --head fix/329-loopback-capability --state open \
  --json number --jq '.[0].number')
PR_346=$(gh pr list --head feat/346-stdio-default --state open \
  --json number --jq '.[0].number')
gh pr view "$PR_329" --json statusCheckRollup,mergeStateStatus
gh pr view "$PR_346" --json statusCheckRollup,mergeStateStatus
```

Both PRs must be clean and all checks successful. The maintainer controls the
coordinated merge.

- [ ] **Step 5: Close the parent roadmap**

After both changes are on `main`, verify #348 acceptance criteria and close it
only if the stdio-default user flow is complete.
